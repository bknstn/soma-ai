# Assistant acceptance and issue #2 coverage

All automated scenarios use synthetic identities, data and transports. CI never calls a live model, Telegram or a health account. The supported Hermes/Health OS revisions remain pinned. The following maps the requested capabilities to reviewable code and tests; manual scenarios are instructions for an operator using a disposable runtime.

## Disposable manual scenarios

1. **Long task:** enable progress in a disposable configured gateway and use a neutral task that genuinely lasts past the selected interval. Expect one factual notice, no percentage, and a final result. Repeat with a native approval/input wait, cancellation and `/new`; verify no later stale notice. The offline tests use controlled clocks rather than a live provider.
2. **New day:** choose an IANA timezone and exact greeting/continuation phrases in private settings. Send a neutral message on day one, then a configured greeting on the next local day. Expect a new native session and the same confirmed synthetic commitment. A same-day greeting, continuation request, forwarded greeting, replay or unknown metadata must not reset. Repeat with a queued request, active/background work and a DST boundary; work must remain intact. Unit tests use explicit timestamps; do not change a production host clock.
3. **Compression:** add and explicitly confirm a synthetic commitment; inspect its stable ID. Exercise the configured native compression threshold, then start a fresh session. Verify the next turn receives the current bounded ledger snapshot, including omission counts when full. Correct/cancel/complete only through explicit confirmation; silence cannot complete a task. Use offline budget preview where no model is configured.
4. **Scheduled follow-up:** explicitly enable both components and the allowed `continuity` source. In a synthetic DM ask conversationally to enable reminders, listen to the explanation, and confirm in different wording on the next turn; repeat using voice. Add a synthetic commitment conversationally and set a disposable near-future daily preparation time. Expect one neutral actionable notice outside quiet hours; unchanged preparation must stay silent. Ask naturally to pause, snooze, focus away from commitments or mute suggestions, then restart: each gate must hold. Resume and confirm a new ledger revision; only a fresh allowed result may notify. Replaying an ambiguous failed attempt must remain silent.
5. **Improvement review:** supply explicit frequency feedback conversationally, then ask whether anything about the assistant could be improved. Expect a concise proposal and an ordinary approval question, subject to the same delivery gate. Verify no code/config/dependency/service/permission change occurs. Repeat unchanged evidence after the review interval: no duplicate proposal. Also request a concrete lower reminder frequency and verify the actual bounded per-DM preferences, including after restart.
6. **Install/disable/rollback:** repeat setup and compare settings/state; explicitly disable the plugin and restart. No supervised timer or boundary/control hook may run. Reenable using the same state and verify no old notice is replayed. Disable before restoring an earlier code revision; preserve state and remove only obsolete code assets if necessary.
7. **Concise replies:** in a disposable runtime, use synthetic text and voice requests for a simple answer, training report, workout history and an unavailable action. Expect an outcome first, one to three short sentences or a compact list/table, no routine narration, and a direct known reason for an unavailable action. Preserve requested exercise values, units, practical safety constraints and unknown write outcomes. Wearable values have inline provider attribution; routine health replies have no local source list or validation audit. Request a detailed explanation and expect the requested depth; the next simple question should be brief again. Repeat in Russian and English. Offline persona tests verify safe migration of both policy blocks, not live model compliance.
8. **Training with incomplete evidence:** use synthetic preparation results with sufficient recovery, insufficient same-source baseline coverage, missing current measurements, a partial profile, a conflicting restriction and an ambiguous per-hand weight. Expect the planned session and available exercise values without status codes, baseline arithmetic, card-validation narration, stale-memory inventories or a local sources footer. With unavailable recovery, expect one practical sentence distinguishing planned weights from today's load; never a positive readiness claim or an invented lighter prescription. A conflicting restriction must still block that movement, and unresolved restrictions must still prevent endorsement of affected exercises or loads. Ambiguous weights and missing durations must not be filled in. Ask explicitly why recovery could not be calculated or which local sources were used; expect the actual available explanation then. Public web research must retain citations. These are manual model-acceptance scenarios, not guarantees from offline prompt tests.

Remove the entire disposable runtime and any task-created helpers after acceptance. Preserve real user state and private deployment configuration. Live manual checks are an operator acceptance workflow; the automated suite uses fake messaging, controlled clocks and fresh synthetic SQLite files.
